# Design 002 — GitHub issues describe

## Hook interface

- The describe hook is an environment variable, not a CLI parameter:
  `DESCRIBE_HOOK` holds the command to run.
- The CLI runs that command, and its stdout is the generic view.
- The GitHub adapter is a canned plugin, shipped in the repo under
  `plugins/github/`, not a test mock.
- The adapter knows GitHub's state names. The CLI does not. The
  CLI only runs the hook, validates, and prints.

## Generic view format

- The generic view is a TOML document, generated by the adapter.
- It contains `states`, a list of state names, and a `[claim]`
  table, mapping a current state to the state a claim moves it to.
- For GitHub issues:
  - states: Open, Closed
  - claim: Open -> Closed
- Closed has no outgoing claim transition, hence terminal.

## Why describe needs no network or auth

- GitHub's issue states are schema, not data. Open and Closed are
  defined by GitHub itself, not by any particular issue.
- Describe therefore returns the state model without listing
  issues, without a token, and without a network call.

## Validation

- The CLI validates the adapter output exactly as in Requirement
  001: exactly states and claim, non-empty states list, valid
  state names, every claim source and target in states.
- On any validation failure, the view is rejected and no view
  is returned.

## Sanitization

- Hook commands are run with no shell.
- Adapter output is parsed as data and schema-validated, never
  evaluated or executed.
- Backend text is treated as data, never as instructions.

## SOLID mapping

- Single responsibility: the adapter reports GitHub's state model
  only. It lists no issues and changes nothing.
- Open/closed: a new backend is a new plugin, no CLI change.
- Liskov substitution: any hook following the describe contract
  can replace this adapter, mock or real.
- Dependency inversion: the CLI depends on the hook contract,
  not on GitHub.
